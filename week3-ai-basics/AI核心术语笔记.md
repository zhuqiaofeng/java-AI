## 0. 先建立一张总图：一次大模型调用到底发生了什么

```
你的 Java/Python 代码
   │  ① 组装 messages（system + user）+ 参数（model/temperature/max_tokens）
   ▼
HTTP POST  /chat/completions          ← 请求体就是一个 JSON，没有魔法
   │  ② 鉴权：Authorization: Bearer sk-xxx
   ▼
大模型服务（云端 GPU 集群）
   │  ③ 分词 Tokenizer：把文字切成 token（"你好" → [1234, 5678]）
   │  ④ 前向计算（Transformer）：根据已有 token 预测"下一个 token"的概率分布
   │  ⑤ 采样：按 temperature/top_p 从概率分布里挑一个 token
   │  ⑥ 把挑中的 token 拼回历史，回到 ④，循环直到遇到停止条件
   ▼
HTTP 响应
   ├─ 非流式：等全部生成完，一次性返回完整 JSON（含 usage 用量）
   └─ 流式（SSE）：每生成几个 token 就推一个 data: 帧回来，前端逐字渲染
```

**一句话记住：大模型 = 一个"给定上文、预测下一个 token"的概率函数。**
它不查数据库、不联网、没有记忆（记忆是你在 messages 里重复带上去的），也不保证说的是真的。

## 2. Transformer 与注意力（懂到能听懂面试题即可）

- **Transformer**：2017 年论文《Attention Is All You Need》提出的网络结构，现在是所有主流 LLM 的骨架。
- **自注意力 Self-Attention**：处理当前 token 时，给上文每个 token 算一个"相关性权重"，加权汇总信息。
  - 类比：`context = Σ(weight_i * value_i)`，本质是一次加权求和，和你在 Java 里做加权平均没区别，只是维度高、参数是学出来的。
- **多头 Multi-Head**：并行做多组注意力，分别捕捉语法、指代、语义等不同关系。
- **位置编码 Positional Encoding**：注意力本身不区分顺序，需要额外注入"第几个位置"的信息（RoPE 是现在主流做法）。
- **Decoder-only**：GPT/Qwen/DeepSeek 都是"只解码"结构，所以只能"从左往右续写"，这也是它天然适合流式输出的原因。
- **参数量 Parameter**：模型里可学习的权重个数，7B = 70 亿。粗略估算显存：FP16 每参数 2 字节 → 7B 模型约 14GB 权重，加上 KV Cache 还要更多。

**面试常问**：为什么 Transformer 取代 RNN？→ 并行度高（训练时不吃序列依赖）、长距离依赖建模好、可堆叠扩展。

## 3. Token：最容易被忽视、但天天影响你的概念

### 3.1 是什么

**Token = 模型处理文本的最小单位**，由分词器（Tokenizer，主流算法 BPE）切出来。它不等于"字"，也不等于"单词"。

```
"Java如何整合SpringAI"  → 可能切成 ["Java", "如何", "整合", "Spring", "AI"]  （5 个 token 左右）
"Hello, world!"         → ["Hello", ",", " world", "!"]                     （4 个 token）
```

经验值（用于心算，最终以 API 返回的 `usage` 为准）：

| 文本类型 | 粗略换算 |
|---|---|
| 中文 | 1 个汉字 ≈ 1~1.5 token |
| 英文 | 1 个单词 ≈ 1.3 token；4 个字符 ≈ 1 token |
| 代码 | 比自然语言更"碎"，同样字数 token 更多（符号、缩进都算） |
| JSON | 同上，`{"key": "value"}` 里的符号都占 token |

### 3.2 为什么必须懂

1. **计费按 token**：输入 token + 输出 token 分别计价，通常输出比输入贵 2~4 倍。
2. **上下文窗口（Context Window）按 token 算**：窗口 = 一次请求里「输入 + 输出」的总 token 上限。常见 32K / 128K / 256K / 1M。
3. **超出窗口**会报错或截断，这就是 RAG 要"切片"、Agent 要"上下文压缩"的根本原因。
4. **性能**：输入 token 越多，首 token 延迟（TTFT）越高，费用也线性上涨。

> 第 3 周的实验脚本 `04_token_experiment.py` 会让你亲眼看到：同一段话的中文版和英文版，`prompt_tokens` 差多少。

## 4. Prompt：你唯一能"编程"模型的地方

### 4.1 三种角色 message

| role | 作用 | Java 类比 |
|---|---|---|
| `system` | 设定身份、规则、输出格式、禁止事项。优先级最高 | 全局配置 / AOP 切面里的统一约束 |
| `user` | 用户这一轮的输入 | 业务请求参数 |
| `assistant` | 模型历史回复（多轮对话时由你回填） | 上一轮响应，用来维持上下文 |
| `tool` | 工具调用结果回填（Function Calling 用） | RPC 返回值 |

多轮对话的真相：**服务端不存你的对话**。你每次都要把历史 messages 一起发上去，token 费也就这么涨上去了。

### 4.2 常用技巧

- **角色设定**：`你是一名资深 Java 架构师，回答必须给出可运行代码。`
- **格式约束**：`严格输出 JSON，字段为 {"title": "...", "points": [...]}，不要解释。`
- **Few-shot 少样本**：给 2~3 个"输入→期望输出"的样例，比写一堆规则更有效。
- **CoT 思维链**：`请先分步骤推理，再给结论`（推理模型如 DeepSeek 思考模式内部已自带）。
- **防幻觉约束**：`只依据<资料>回答；资料中没有的内容，直接回答"资料未提及"。`
- **Prompt 注入防护**：用户输入里可能有"忽略以上指令"，要在 system 层声明优先级并做输入过滤（第 11 周专题）。

## 5. 采样参数：控制"稳定性 vs 创造力"

| 参数 | 含义 | 取值建议 |
|---|---|---|
| `temperature` | 概率分布的"平滑程度"。越小越确定、越保守；越大越发散 | 事实问答/代码 0~0.3；创意 0.7~1.0 |
| `top_p` | 核采样：只在累计概率前 p 的候选里挑 | 与 temperature 二选一调，默认 1.0 |
| `max_tokens` | 输出上限，防止话痨+控成本 | 摘要 256，长文 2048 |
| `stop` | 命中这些字符串就停止生成 | 自定义格式结尾标记 |
| `frequency_penalty` / `presence_penalty` | 抑制重复 / 鼓励新话题 | 一般不动 |
| `response_format` | 要求返回 JSON（`json_object`） | 结构化输出必开 |
| `seed` | 尽量让结果可复现（不保证 100%） | 测试用 |

**temperature = 0 也不是完全确定**——GPU 浮点运算和批处理顺序会带来细微差异，别拿它当"幂等"用。

## 6. Embedding：把文字变成向量（RAG 的地基）

- **定义**：Embedding 模型把一段文本映射成一个固定维度的浮点数组，例如 `float[1024]`。
- **核心性质**：语义越相近，向量距离越近。所以"怎么退款"和"如何申请退货"即使没有一个字相同，向量也很接近——这是关键词搜索做不到的。
- **注意**：Embedding 模型和对话模型是两个模型，两个接口。对话模型 `qwen-plus` 不能拿来算向量，要用 `text-embedding-v3/v4` 这类。

### 6.1 余弦相似度（必须会手算）

```
cos(A,B) = (A·B) / (|A| * |B|)
```

举例：A = [1, 2], B = [2, 4]
- 点积 A·B = 1×2 + 2×4 = 10
- |A| = √5 ≈ 2.236, |B| = √20 ≈ 4.472
- cos = 10 / (2.236×4.472) ≈ **1.0** → 完全同向（语义几乎一致）

B = [4, -2] 时：点积 = 4-4 = 0 → cos = 0 → 正交（语义无关）。

- 取值 [-1, 1]，越大越相似。工程上常把向量**归一化**（长度=1）后直接用点积，省掉除法。
- 高维空间里"距离"会失效（维度灾难），所以用余弦而不是欧氏距离。

### 6.2 Java 侧怎么存

- 存 `float[]` 或用 `List<Float>`，落库时序列化成 JSON/二进制；
- 向量库（Redis Vector / Milvus / PGVector）内部用 HNSW、IVF 等**近似最近邻 ANN** 算法，牺牲极小精度换毫秒级检索；
- 第 6 周你会用 Redis Vector 亲手建索引（`FT.CREATE ... VECTOR HNSW`）。

## 7. RAG：检索增强生成（岗位最高频）

### 7.1 为什么需要

| 大模型的天然缺陷 | RAG 怎么解决 |
|---|---|
| 知识有截止日期，不知道你公司今天的规定 | 把最新文档检索出来塞进 prompt |
| 没见过你的私有数据（订单、合同、代码库） | 同上，数据不进模型参数，只进上下文 |
| 容易幻觉，编造不存在的条款 | 要求"只依据资料回答"，并给出出处 |
| 微调成本高、更新慢 | 改文档即可，无需重训 |

**一句话：RAG = 检索（找资料）+ 增强（拼进 prompt）+ 生成（模型作答）。**
它不是训练，本质是"开卷考试"。

### 7.2 完整链路（第 6~7 周要一行行写出来）

```
【离线入库】
1. 文档上传      → 存原始文件（MinIO/OSS/本地）
2. 解析 Parse    → Tika/POI 把 PDF/Word 抽出纯文本
3. 切片 Chunk    → 按 500~800 字 + overlap 100 切块（Token 数控制）
4. 向量化 Embed  → text-embedding 模型，每块 → float[1024]
5. 入库 Index    → 向量库存 (id, 向量, 文本, 元数据：文件名/页码/章节)

【在线问答】
6. 问题向量化    → 同一个 embedding 模型（必须同一模型！否则空间不对齐）
7. 向量检索 TopK → ANN 召回最相似的 3~5 块，可加元数据过滤
8. 重排 Rerank   → （可选）交叉编码器精排，把最相关的排前面
9. 拼 Prompt     → "仅根据以下资料回答……资料：[1]…[2]… 问题：…"
10. 生成 + 溯源  → 模型作答，同时把命中的 chunk 来源返回给前端
```

### 7.3 切片策略

| 策略 | 做法 | 适用 |
|---|---|---|
| 固定长度 | 每 N 字符/Token 一刀 | 最简单，会切断句子 |
| 递归字符 | 先按段落，再按句号，再按逗号，递归到长度达标 | **默认首选**（LangChain/Spring AI 的 TokenTextSplitter 思路） |
| 语义切片 | 用 embedding 判断句子间语义突变处断开 | 精度高、成本高 |
| 结构化切片 | 按 Markdown 标题 / 表格行 / 代码块切 | 技术文档、规章 |

关键参数：**chunk_size 与 overlap**。overlap 是为了防止"答案正好被切断在两块之间"。

### 7.4 进阶优化（第 9 周）

- **Rerank 重排**：向量召回是"粗筛"，用 bge-reranker 之类做精排，准确率提升明显。
- **多路召回**：向量 + 关键词 BM25 + 元数据过滤，合并去重。
- **上下文压缩**：召回后先让模型/规则压缩成要点，再拼 prompt，省 token。
- **查询改写**：把"它怎么收费"改写成"XX 产品收费标准"，解决指代和口语化。

## 8. Agent 与 Function Calling

### 8.1 区别：Workflow vs Agent

- **Workflow（工作流）**：路径你写死。`if 用户问订单 → 查订单表`。稳定、可控、便宜。
- **Agent（智能体）**：路径模型自己选。你只给它一堆工具和描述，它自己决定"要不要调、调哪个、传什么参数、调几次"。

> 工程经验：**能用 Workflow 就别上 Agent**。Agent 更贵、更慢、更不可预测；只用在"意图开放、步骤不定"的场景。

### 8.2 Function Calling 的时序（第 8 周核心）

```
1. 你先把工具清单（JSON Schema）随请求发给模型：
   tools = [{name:"queryOrder", description:"按订单号查订单状态", parameters:{orderNo:"string"}}]
2. 模型判断需要调工具，返回的不是文本，而是：
   {"tool_calls":[{"id":"call_1","function":{"name":"queryOrder","arguments":"{\"orderNo\":\"A1001\"}"}}]}
3. 你的 Java 代码解析 tool_calls，反射/路由到真正的业务方法，拿到结果
4. 把结果以 role=tool（带 tool_call_id）回填进 messages，再次请求模型
5. 模型基于工具结果生成最终自然语言回答
```

**要点**：
- 模型**不会**真的执行你的代码，它只是"输出一段表示要调用的 JSON"。执行权始终在你的系统里——这是安全边界。
- 工具描述（description）写得好不好，直接决定模型选不选得对，相当于"给新员工写 API 文档"。
- Spring AI 用一个 `@Tool` 注解 + `ToolCallback` 就把上面 1~5 步封装了。

## 9. SSE 流式输出：打字机效果的实现原理

### 9.1 协议长什么样

HTTP 响应头：`Content-Type: text/event-stream`，连接保持不关，服务端持续写入：

```
data: {"choices":[{"delta":{"content":"你"}}]}

data: {"choices":[{"delta":{"content":"好"}}]}

data: [DONE]
```

每条消息以 `data: ` 开头，两个换行 `\n\n` 表示一条事件结束。客户端逐条解析、逐字渲染。

### 9.2 为什么用 SSE 而不用 WebSocket

| 对比 | SSE | WebSocket |
|---|---|---|
| 方向 | 服务端 → 客户端 单向 | 双向 |
| 协议 | 普通 HTTP/1.1（可 HTTP/2） | 需协议升级 |
| 穿透性 | 过网关、代理友好 | 部分代理会拦 |
| 断线重连 | 浏览器 EventSource 自带 | 要自己实现 |
| 适合 | LLM 逐字输出 | 聊天室、协同编辑 |

LLM 场景是典型的"一问一答、服务端单向推"，所以 SSE 够用且更轻。

### 9.3 Java 侧两种实现（第 4 周）

- **Spring MVC**：`SseEmitter`，手动 `send()`，注意设置超时和异常回调；
- **WebFlux（推荐）**：Controller 直接返回 `Flux<String>`，`produces = TEXT_EVENT_STREAM_VALUE`，背压由 Reactor 处理。
- Spring AI 的 `chatClient.prompt().stream().content()` 返回的就是 `Flux<String>`。

### 9.4 工程坑

- Nginx 会缓冲响应 → 必须 `proxy_buffering off;`，否则"流式"变"一次性"；
- 中间层超时要调大（`proxy_read_timeout`）；
- 客户端断开要能感知并取消上游请求，否则 GPU 白烧钱。

## 10. 幻觉（Hallucination）与它的对手们

| 手段 | 原理 | 成本 |
|---|---|---|
| Prompt 约束 | "只依据资料回答，否则说不知道" | 极低 |
| RAG | 把事实塞进上下文 | 中 |
| 降低 temperature | 减少发散 | 极低 |
| 引用溯源 | 强制模型给出来源，便于人工核对 | 低 |
| 结构化输出 + 校验 | JSON Schema 校验，不合格重试 | 低 |
| 微调 SFT | 把领域知识/风格写进参数 | 高 |
| 人工审核 / 兜底话术 | 高风险场景必须有人 | 中 |

**认知：幻觉不可能被彻底消除**（本质是概率生成）。工程上要的是"可检测、可兜底、可追溯"。

## 11. 微调家族：SFT、RLHF、LoRA、蒸馏、量化

| 名词 | 全称/含义 | 一句话 |
|---|---|---|
| **SFT** | Supervised Fine-Tuning 监督微调 | 用"问题-标准答案"对喂给模型，教它按你要的格式/风格回答 |
| **RLHF** | Reinforcement Learning from Human Feedback | 人类给回答打分，训练奖励模型，再用强化学习优化，让回答更"符合人类偏好" |
| **DPO** | Direct Preference Optimization | RLHF 的简化版，直接用"好/坏"成对数据优化，不用奖励模型 |
| **LoRA** | Low-Rank Adaptation | 冻结原模型，只训练少量低秩矩阵，用 1% 的显存完成微调 |
| **QLoRA** | 量化 + LoRA | 4bit 量化基座 + LoRA，单卡可微调 7B |
| **蒸馏 Distillation** | 大模型教小模型 | 用大模型的输出当训练数据，让小模型学会它的能力 |
| **量化 Quantization** | FP16 → INT8/INT4 | 降显存、提速度，精度略降（GPTQ/AWQ/GGUF） |
| **RAG vs 微调** | 知识 vs 行为 | "知道什么"用 RAG；"怎么说话/什么格式"用微调 |

## A.1 五次非流式调用

| # | 场景 | prompt_tokens | completion_tokens | total | 耗时 | finish_reason |
|---|---|---|---|---|---|---|
| 1 | 解释 RAG（t=0.7，max=512） | 49 | 130 | 179 | 4547 ms | stop |
| 2 | 给猫起名（t=0.0，max=512） | 47 | 407 | 454 | 11401 ms | stop |
| 3 | 给猫起名（t=1.0，max=512） | 47 | 457 | 504 | 12751 ms | stop |
| 4 | CAP 理论（max=30） | 48 | 30 | 78 | 2036 ms | **length** |
| 5 | 多线程·小学生人设（max=512） | 28 | 512 | 540 | 14920 ms | **length** |
| 6 | 同上，max 调到 1024 | 28 | 570 | 598 | 13809 ms | stop |

**可以读出来的四件事：**

1. **中文大约 1 字 ≈ 1 token。** 第 1 次输入是一个 45 字的 system 提示 + 9 字的问题，合计 49 token，几乎 1:1。
2. **同一个 prompt 的 prompt_tokens 是稳定的。** 第 2、3 次输入完全相同（只有 temperature 不同），prompt_tokens 都是 47——temperature 不影响计费。
3. **默认 512 的 max_tokens 会不够用。** 同一问题把上限调到 1024 后，真实输出是 570 个 token、`finish_reason=stop`——512 差了 58 个 token，用户看到的就是"说到一半没了"。**max_tokens 要按场景实测，不能拍脑袋。**
4. **输出速度约 30~36 token/秒。** 130 token 用 4.5 s、407 token 用 11.4 s、512 token 用 14.9 s，量级一致；长回答的耗时主要花在逐 token 解码上。

## A.2 成本换算（示例单价：输入 2 元/百万、输出 6 元/百万）

| 场景 | 输入成本 | 输出成本 | 单次合计 |
|---|---|---|---|
| 解释 RAG（49 + 130） | 0.000098 元 | 0.00078 元 | **≈ 0.00088 元** |
| 给猫起名（47 + 457） | 0.000094 元 | 0.002742 元 | **≈ 0.00284 元** |

按"给猫起名"这种长回答的计算方式，1000 次/天 ≈ **2.84 元/天**，一个月 ≈ **85 元**。输出 token 占了成本的 97%。

## A.3 一次流式调用的原始报文（`03_chat_stream.py --raw`）

- 第一条帧只有 `"delta":{"content":"","role":"assistant"}`，内容为空——**首帧只声明角色**；
- 后续帧的 `delta.content` 有时是 1 个字（`"S"`），有时是好几个 token（`"SE（Server"`、`"-Sent Events"`）——**服务端会攒几个 token 一起推，所以"块数"≠"token 数"**；
- 每帧都带 `"usage":null`，整段结束也没返回用量——**Qwen 的流式默认不返回 usage**，要统计 token 只能自己估算，或另发一次非流式请求兜底。

## A.4 三条结论（自己补全）

1. 我实测：152 个汉字 ≈ 117 token（约 0.77 token/汉字，反过来约 1.3 汉字/token）；英文约 4.7 字符 ≈ 1 token。（短句因为标点和英文夹杂，会接近 1:1，长文本才看得出 0.8 的系数）
2. 我的默认 `max_tokens` 设置为 __512__ 时，__讲给孩子听、写长文、代码生成__ 场景会被截断；工程上应该 __按场景调大（1024~2048）__。
3. 流式请求里统计 token 的正确做法是 __流式时用本地估算 + 非流式兜底采样__。

# 附录 B：Day1–Day3 课堂问答记录

## B.1 三个概念题

**Q1：为什么 "Token" 只切 1 个 token，"句" 却要 2 个？**

> 答：英文常见词在语料里经常出现，已经被合并，所以分词时只占一个 token；中文在字节级 BPE 里常被拆成"半个字的字节碎片"，所以部分生僻字会被算成 2 个 token。

批注：正确。这个机制叫 **Subword（子词）分词**：词表大小有限（几万~十几万），没有整体条目的字只能按字节切。UTF-8 下一个汉字占 3 字节，词表里没有它，就退化成字节碎片。

**Q2：中文 73 token、英文 45 token，对产品设计有什么影响？**

> 初答：应使用模型训练语料更丰富的语言；英文理解精度更高，适合专业与学术领域；中文适合中文语境、创意写作和本地化内容；但要避免中英混排，频繁切换会使理解精度下降并消耗更多 token。

批注：方向对，但混了两个概念。**token 效率 ≠ 语义理解能力**：英文 token 少只影响成本和上下文占用；理解能力取决于训练语料分布（Qwen 中文语料占比高，中文并不弱）。混排的真实代价是 **token 变多 + 风格漂移**，不是"精度下降"。工程结论：**prompt 语言、文档语言、期望回答语言保持一致**。

实测修正：Qwen 分词器下反而是**中文更省 token**（152 汉字 ≈ 117 token，同义英文 ≈ 133 token），详见附录 A。

**Q3：`finish_reason = length`，最可能出了什么问题？**

> 答：模型还没写完，输出配额就用完了，`max_tokens` 太小导致截断，应先调 `max_tokens`。

批注：正确，但漏了第二种可能——**prompt 太长把上下文窗口占满**，留给输出的空间不足，这时调 `max_tokens` 没用，要先看 `usage.total_tokens`。工程动作：打印 `usage` 和 `finish_reason` → 判断是配额问题还是窗口问题 → 再决定调参、裁历史还是切片；并把 `finish_reason` 写进日志。

## B.2 余弦相似度两题

**Q1：为什么检索用余弦，不用欧氏距离？**

> 答：余弦只关注夹角方向，不关心向量长短，主题相同但长度差异大的文章相似度依然很高；欧氏距离是高维空间的绝对直线距离，同时受方向和长度影响，长文档向量模长偏大会被拉远，导致语义相近却被误判为不相似。

批注：正确。补一个等价的工程事实：**对归一化向量，欧氏距离与余弦是单调等价的**（‖a−b‖² = 2 − 2cos），排序结果完全一致。所以"用哪个"取决于是否先归一化；生产环境统一归一化后，直接点积最快。

**Q2：doc-2 改成 `[2.0, 4.0]`，cos 是多少？**

> 答：cos = 1.0。把向量看成箭头，余弦只看箭头指向的角度，不看箭头长度。长度对相似度没有影响，分母的归一化会消去长度影响。

批注：正确。手算：`(1×2 + 2×4) / (√5 × √20) = 10 / 10 = 1.0`。这解释了为什么"文本越长"不会自动获得更高相似度——这一点在第 6 周调检索参数时直接相关。
